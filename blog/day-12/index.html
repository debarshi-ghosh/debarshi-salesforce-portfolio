Trigger Best Practices: Bulkification and Handler Patterns

Build scalable Apex trigger frameworks with bulkification, handlers, recursion controls and governed bypasses.

Intermediate15–20 min readUpdated: November 2026

Apex triggers execute in response to record changes. Use before triggers to validate or modify incoming records and after triggers for work requiring saved record IDs.

Trigger events and context

Events include insert, update, delete and undelete. Trigger.new and Trigger.old contain records when available; newMap and oldMap provide ID lookups. Before insert has no newMap. Delete has no Trigger.new. Undelete is after-only. After-trigger records are read-only.

trigger AccountTrigger on Account (before insert, before update, after update) {
    if (Trigger.isBefore) {
        for (Account a : Trigger.new) {
            if (String.isBlank(a.Description)) {
                a.Description = 'Pending review';
            }
        }
    }
}

Execution lifecycle

Bulkification and handlers

Use one trigger per object and delegate to a handler. Process collections, query once outside loops, and perform DML on collections. Trigger batches can contain 200 records.

trigger AccountTrigger on Account (after update) {
    AccountHandler.afterUpdate(Trigger.new, Trigger.oldMap);
}
public class AccountHandler {
    public static void afterUpdate(List<Account> records,
                                   Map<Id, Account> oldMap) {
        Set<Id> changed = new Set<Id>();
        for (Account a : records) {
            if (a.Name != oldMap.get(a.Id).Name) changed.add(a.Id);
        }
        if (changed.isEmpty()) return;
        List<Contact> contacts = [
            SELECT Id, AccountId, Description FROM Contact
            WHERE AccountId IN :changed
        ];
        for (Contact c : contacts) {
            c.Description = 'Account name changed';
        }
        update contacts;
    }
}

Use field-change detection rather than a blanket static Boolean recursion guard. Consider idempotency, sharing and CRUD/FLS requirements, row limits and asynchronous processing for high fan-out. Test 200 records, unchanged values, failures and repeated execution.

Trigger framework architecture

A thin trigger delegates context to a handler, which dispatches to operation-specific services. Keep orchestration separate from business rules and data access. A framework can standardize dispatch, execution order, observability and bypass policy, but Salesforce does not prescribe a single framework implementation.

Controlled bypasses

Bypass only explicitly approved handlers, never all automation. Use a transaction-scoped set of handler keys, restrict entry points, and restore state in finally. Static state does not cross asynchronous transactions. Never bypass mandatory security or compliance validation.

public class TriggerControl {
    private static Set<String> bypassed = new Set<String>();
    public static void bypass(String key) { bypassed.add(key); }
    public static void clear(String key) { bypassed.remove(key); }
    public static Boolean isBypassed(String key) {
        return bypassed.contains(key);
    }
}

Check the handler key before dispatch. A privileged integration can enable the bypass immediately before its DML and clear it in a finally block. In a nested invocation preserve the prior bypass state rather than clearing another caller’s bypass. A bypass is not authorization: enforce permissions at the entry point and audit its use.

Recursion and idempotency

Prefer old/new field comparisons and idempotent writes. If a transaction-scoped processed set is necessary, key it by operation and record ID, not a single static Boolean. Before insert has no IDs; design a stable business key or avoid recursion there. Static guards can suppress legitimate subsequent updates and must be tested across repeated trigger invocations.

Production considerations

  • Query related records once and group them by parent ID. Avoid unnecessary updates and high fan-out synchronous work.
  • Document handler order, ownership and failure policy. Use partial DML only when business semantics permit it.
  • Enforce sharing, CRUD and field-level security according to the execution context. Test bypass authorization and cleanup.
  • Test insert, update, delete, undelete, 200-record batches, negative paths, recursion and asynchronous boundaries.

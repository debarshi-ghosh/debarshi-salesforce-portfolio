Salesforce Data Model Explained: Objects, Fields, Records & Relationships

A practical guide to designing a Salesforce data model that is understandable, secure, scalable and ready for real business processes.

Beginner to intermediate14–18 min readUpdated: November 2026

Every Salesforce implementation is built around data. Sales teams work with accounts, contacts and opportunities. Service teams manage cases, assets and entitlements. Industry solutions add specialized objects, while custom business requirements introduce custom objects and fields.

Understanding the Salesforce data model means understanding how that information is structured, connected, secured and queried. A good data model does more than store records: it reflects the business, supports automation and reporting, and avoids unnecessary complexity.

Core idea: An object is comparable to a database table, a field to a column, and a record to a row. This analogy is useful, but Salesforce adds platform metadata, relationship behavior, security and automation around those structures.

1. The building blocks: objects, fields and records

Objects

An object is a container for a particular type of information. Salesforce provides standard objects such as Account, Contact, Lead, Opportunity and Case. You can also create custom objects to represent business concepts that are not covered by the standard model.

Fields

Fields describe the attributes stored on an object. For example, an Account can have fields such as Name, Industry, Phone and Website. Custom fields use the __c suffix in their API names, such as Customer_Tier__c.

Records

A record is an individual instance of an object. “Acme Manufacturing” can be one Account record; “Jane Smith” can be one Contact record. Each record has an ID that uniquely identifies it in the org.

2. Standard objects vs. custom objects

Start with standard objects when they already represent the business concept. Standard objects come with established platform behavior and relationships. Create a custom object when the business needs a distinct entity that the standard model does not represent appropriately.

Standard objectTypical purpose
AccountOrganizations or people with whom the business has a relationship
ContactPeople associated with accounts
LeadProspective customers before qualification
OpportunityPotential revenue and sales deals
CaseCustomer issues or service requests

Example custom objects might include Installation__c, Warranty_Claim__c or Service_Visit__c. The API name matters in Apex, SOQL, integrations and metadata deployments, so choose names that are meaningful and consistent.

3. Field types and choosing the right one

Field types influence what users can enter, how values are stored, what validations are possible and how data can be queried.

  • Text / Text Area: names, codes, descriptions and notes.
  • Number / Currency / Percent: quantities, monetary values and rates.
  • Date / DateTime: business dates versus a precise point in time.
  • Checkbox: a true/false attribute.
  • Picklist: a controlled set of choices; use global value sets when values should be shared.
  • Formula: a calculated value derived from other fields; it is not directly edited by users.
  • Roll-Up Summary: an aggregate of related detail records in supported master-detail relationships.
  • Lookup / Master-Detail: relationship fields that connect records.
  • Geolocation: latitude and longitude values for location-aware use cases.
Design tip: Do not use a free-text field for values that must follow a controlled vocabulary. Conversely, do not turn every changing business value into a picklist without considering maintenance, integrations and reporting.

4. Relationships: how records connect

Relationships are represented by relationship fields. The main relationship types used in Salesforce data modeling include lookup and master-detail. Specialized relationship fields are available for external objects, and the User object supports a hierarchical relationship.

Lookup relationship

A lookup links one record to another without the same degree of dependency as master-detail. The related record generally remains an independent record. Lookup fields are not automatically required, and lookup relationships do not provide the native roll-up summary behavior of master-detail relationships.

Example: A custom Installation__c record can look up to an Account. An installation may be associated with a customer account, while the installation record has its own lifecycle and ownership considerations.

Master-detail relationship

A master-detail relationship tightly couples the detail record to its master. The master controls important aspects of the detail record, including access behavior. Deleting the master deletes its related detail records. The detail record does not have independent ownership in the same way as a standalone lookup child, and roll-up summary fields can aggregate detail records on the master.

Example: An Invoice_Line__c could be a detail of an Invoice__c when a line item has no meaningful lifecycle outside its invoice.

ConsiderationLookupMaster-detail
Relationship couplingLooserTighter
Child can exist independentlyUsually yesNo; it depends on its master
Parent deletionDoes not generally cascade-delete the lookup childDeletes related detail records
Access behaviorChild access is managed independentlyDetail access is controlled through the master
Native roll-up summaryNot supported directlySupported on the master

There are configuration constraints and exceptions, so check the object-specific relationship rules before changing a production schema. For example, converting an existing relationship or creating master-detail after records exist can require additional preparation.

Hierarchical relationship

A hierarchical relationship is a special lookup relationship available on the User object. A common use is representing a management chain, such as a user’s manager.

External and indirect lookup relationships

When working with Salesforce Connect external objects, external lookup and indirect lookup relationships can associate records using external identifiers rather than requiring the related records to share Salesforce record IDs. These are specialized patterns; they are not interchangeable with ordinary lookup fields.

5. Many-to-many relationships and junction objects

A many-to-many relationship means records on each side can be associated with multiple records on the other side. A common Salesforce modeling approach is a junction object with two master-detail relationship fields.

Example: Consultants and Projects. A consultant can work on several projects, and each project can have several consultants. Create a custom junction object such as Project_Assignment__c with master-detail relationships to Consultant__c and Project__c.

  • Consultant__c — one side of the relationship
  • Project__c — the other side
  • Project_Assignment__c — the junction, optionally storing Role, Start Date, Allocation Percentage and Status

The junction object is valuable because the relationship itself often has business attributes. Allocation percentage belongs to the consultant-project assignment, not necessarily to the consultant or project alone.

6. A practical Sales Cloud data model

Consider a manufacturing company managing customers, sales opportunities, products and quotations. A simplified conceptual model could look like this:

Account
  ├── Contact
  └── Opportunity
        └── Quote
              └── Quote Line Item
                    └── Product

This is a conceptual view, not a complete declaration of every Salesforce relationship. Standard Salesforce objects have predefined relationships and constraints; verify the exact object model in your org and the current Object Reference before implementing extensions.

Suppose the business also needs to track site installations. You might add Installation__c related to Account and, where appropriate, Opportunity. If an installation has multiple visits, a separate Service_Visit__c object could be related to Installation. Decide whether each visit is a dependent child or an independently managed record before choosing master-detail or lookup.

7. Querying relationships with SOQL

Relationship design affects how developers retrieve data. SOQL supports child-to-parent traversal using relationship fields and parent-to-child queries using relationship subqueries.

Child-to-parent query

From Contact to its Account, use dot notation:

SELECT Id, Name, Account.Name, Account.Industry
FROM Contact
WHERE AccountId != null

Parent-to-child query

From Account to its Contacts, use a child relationship subquery. The relationship name in the subquery is the child relationship name, which can differ from the child object API name:

SELECT Id, Name,
       (SELECT Id, Name, Email FROM Contacts)
FROM Account
WHERE Industry = 'Manufacturing'

Use the correct relationship name from Object Manager or Schema Builder. For custom relationships, the child relationship name is configurable and typically ends with __r in SOQL.

8. Design considerations before creating objects

  • Understand the business entity: Is it a real object with its own lifecycle, or just an attribute of another record?
  • Define ownership and access: Who should own the record, and who should see or edit it?
  • Choose relationship behavior deliberately: Consider independent lifecycle, deletion, sharing and roll-up requirements.
  • Plan for reporting: Will users need reports across these records? Is the relationship structure report-friendly?
  • Consider integrations: Identify external keys, data ownership, matching rules and synchronization direction.
  • Prevent duplication: Use appropriate unique fields, external IDs, matching and duplicate-management strategies.
  • Plan for scale: Consider record volumes, selective filters, ownership skew, sharing recalculation and query patterns.
  • Keep the model understandable: Avoid creating objects and relationships without a clear business purpose.

9. Use Schema Builder to visualize the model

Schema Builder provides a visual way to view objects, fields and relationships in an org. It can also be used to create custom objects, supported custom fields and lookup or master-detail relationships.

  1. Open Setup and search for Schema Builder.
  2. Use the object panel to select the standard and custom objects relevant to your design.
  3. Review the fields and relationship lines to understand the existing structure.
  4. Use the Elements panel to add a custom object or supported field when designing a change.
  5. Review the model with developers, admins, architects and business stakeholders before deploying changes.

Schema Builder is useful for visualization, but it does not replace requirements analysis, data profiling, security design or deployment planning.

10. Common data modeling mistakes

  • Creating a custom object when a suitable standard object already exists.
  • Using master-detail simply to obtain roll-up summaries without considering ownership, sharing and cascade deletion.
  • Storing multiple values in one text field instead of modeling a related child entity where appropriate.
  • Using free text for controlled categories and then struggling with inconsistent reporting.
  • Ignoring external IDs and data ownership in integration-heavy solutions.
  • Changing relationship types without assessing existing records and downstream dependencies.
  • Designing only for the first screen or report instead of the complete business lifecycle.

Key takeaway

A strong Salesforce data model reflects the business clearly and supports the complete record lifecycle. Choose objects based on business entities, fields based on data meaning, and relationships based on dependency, ownership, access and reporting needs. Validate the design with real use cases, integration requirements and expected data volumes before building it.

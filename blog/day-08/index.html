Apex Collections: List, Set and Map with Practical Use Cases

Learn how Apex Lists, Sets and Maps work, when to choose each collection, and how to combine them for bulk-safe Salesforce development.

Intermediate18–22 min readUpdated: November 2026

Salesforce records are frequently processed in groups: an API integration may send hundreds of Accounts, a trigger can receive a batch of records, or a batch job may process large datasets. Apex collections help you store, organize, search and process these values efficiently.

The three core collection types are List, Set and Map. Choosing the right one can simplify code, avoid duplicate work, reduce repeated queries and support bulk-safe designs.

Core idea: Use a List when order and duplicates matter, a Set when you need unique values, and a Map when you need fast key-based lookup.

1. What are collections?

A collection is a data structure that stores multiple values in one variable. Apex supports three primary collection types:

CollectionStoresKey characteristicCommon use
ListOrdered valuesAllows duplicates; index-based accessProcess query results or ordered records
SetUnique valuesDoes not allow duplicate elementsUnique IDs, membership checks
MapKey-value pairsEach key maps to one valueLookup records by ID or code

2. List: ordered collection

A List stores elements in a sequence and allows duplicates. Elements are accessed using a zero-based index.

List<String> regions = new List<String>();
regions.add('East');
regions.add('West');
regions.add('East');

System.debug(regions[0]); // East
System.debug(regions.size()); // 3

Common List methods

MethodPurpose
add(value)Add an element
add(index, value)Insert at a position
get(index) / [index]Retrieve an element
set(index, value)Replace an element
remove(index)Remove an element by index
size()Number of elements
isEmpty()Check whether it contains elements
contains(value)Check whether a value exists
clear()Remove all elements
sort()Sort elements where the element type supports ordering

Practical use: collect records for bulk DML

List<Account> accountsToUpdate = new List<Account>();

for (Account acc : [
    SELECT Id, Type
    FROM Account
    WHERE Type = 'Prospect'
    LIMIT 200
]) {
    acc.Type = 'Customer';
    accountsToUpdate.add(acc);
}

if (!accountsToUpdate.isEmpty()) {
    update accountsToUpdate;
}

Records are accumulated first and updated in one DML statement rather than issuing DML inside the loop. The example includes a limit for illustration; production queries should be designed around actual selectivity and volume requirements.

3. Set: unique values only

A Set stores unique elements. Adding a value already present does not create a second copy. Sets are useful for de-duplication and membership checks.

Set<String> regions = new Set<String>{
    'East', 'West', 'East'
};

System.debug(regions.size()); // 2
System.debug(regions.contains('West')); // true

A Set does not provide a positional index like a List. Do not rely on an iteration order for business sequencing.

Practical use: collect unique parent IDs

List<Case> cases = [
    SELECT Id, AccountId, Subject
    FROM Case
    WHERE AccountId != null
    LIMIT 200
];

Set<Id> accountIds = new Set<Id>();

for (Case caseRecord : cases) {
    accountIds.add(caseRecord.AccountId);
}

List<Account> relatedAccounts = [
    SELECT Id, Name
    FROM Account
    WHERE Id IN :accountIds
];

Even if many Cases belong to the same Account, the Set stores each Account ID once. This is a common pattern for bulk-safe trigger and service logic.

Practical use: prevent duplicate processing

Set<String> processedExternalIds = new Set<String>();

for (String externalId : incomingExternalIds) {
    if (String.isBlank(externalId)) {
        continue;
    }

    if (processedExternalIds.add(externalId)) {
        // This is the first occurrence in this transaction's list.
        processExternalId(externalId);
    }
}

The add() method returns true when the element is newly added and false when it was already present, making it useful for detecting first occurrences.

4. Map: key-value lookup

A Map stores key-value pairs. Each key is unique and points to one value. Maps are especially useful when you need to find a record or calculated value using an identifier.

Map<String, Integer> regionCounts =
    new Map<String, Integer>();

regionCounts.put('East', 12);
regionCounts.put('West', 8);

System.debug(regionCounts.get('East')); // 12
System.debug(regionCounts.containsKey('West')); // true

Common Map methods

MethodPurpose
put(key, value)Add or replace a key-value pair
get(key)Retrieve value for a key; returns null when no mapping exists
containsKey(key)Check whether a key exists
keySet()Return the Set of keys
values()Return a List of values
remove(key)Remove a mapping by key
size()Number of key-value pairs
isEmpty()Check whether the Map is empty
clear()Remove all mappings

Practical use: build a Map of Accounts by ID

List<Account> accounts = [
    SELECT Id, Name, Industry
    FROM Account
    WHERE Industry != null
    LIMIT 200
];

Map<Id, Account> accountsById =
    new Map<Id, Account>(accounts);

for (Case caseRecord : [
    SELECT Id, AccountId, Subject
    FROM Case
    WHERE AccountId IN :accountsById.keySet()
]) {
    Account parentAccount =
        accountsById.get(caseRecord.AccountId);

    System.debug(parentAccount.Name);
}

Apex supports constructing a Map from a List of sObjects. The record IDs become the keys, and the records become the values. This is a common way to avoid repeatedly scanning a List to find a related record.

5. Combining List, Set and Map in bulk-safe Apex

Real projects often use all three collection types together. Consider a trigger handler that receives a List of Cases and needs to update a field based on the related Account's service tier.

public class CaseServiceTierHandler {
    public static void applyServiceTier(List<Case> caseRecords) {
        Set<Id> accountIds = new Set<Id>();

        for (Case caseRecord : caseRecords) {
            if (caseRecord.AccountId != null) {
                accountIds.add(caseRecord.AccountId);
            }
        }

        if (accountIds.isEmpty()) {
            return;
        }

        Map<Id, Account> accountsById =
            new Map<Id, Account>([
                SELECT Id, Service_Tier__c
                FROM Account
                WHERE Id IN :accountIds
            ]);

        List<Case> casesToUpdate = new List<Case>();

        for (Case caseRecord : caseRecords) {
            Account parentAccount =
                accountsById.get(caseRecord.AccountId);

            if (parentAccount != null) {
                caseRecord.Service_Tier__c =
                    parentAccount.Service_Tier__c;
                casesToUpdate.add(caseRecord);
            }
        }

        if (!casesToUpdate.isEmpty()) {
            update casesToUpdate;
        }
    }
}

This example demonstrates the collection pattern, but it should not be copied directly into a before-update trigger because updating the same triggering records again would be unnecessary and could cause recursion. In a before trigger, assign the field directly on the incoming records and do not issue DML for those records. In an after-trigger or service context, decide whether a separate update is actually required.

Bulkification pattern: Start with the incoming List, gather unique related IDs in a Set, query related records once, index them in a Map, then process the original List using Map lookups.

6. Map grouping: one parent to many child records

Sometimes you need the opposite structure: one key mapped to a List of related records. A Map whose values are Lists is a common grouping pattern.

Map<Id, List<Case>> casesByAccount =
    new Map<Id, List<Case>>();

for (Case caseRecord : [
    SELECT Id, AccountId, Subject
    FROM Case
    WHERE AccountId != null
    LIMIT 500
]) {
    if (!casesByAccount.containsKey(caseRecord.AccountId)) {
        casesByAccount.put(
            caseRecord.AccountId,
            new List<Case>()
        );
    }

    casesByAccount.get(caseRecord.AccountId).add(caseRecord);
}

Now the code can retrieve all Cases for a particular Account directly from the Map. This pattern is useful for parent-child calculations, notifications and data transformation.

7. Nested collections

Collections can contain other collections. Common examples include Map<Id, List<Case>>, List<Set<Id>> and Map<String, Map<Id, Decimal>>. Use nested collections when they represent a clear grouping or relationship; avoid unnecessary nesting that makes the data structure hard to understand.

9. Collection performance and common mistakes

  • Use a Map instead of repeatedly looping through a List to find a record by ID.
  • Use a Set to de-duplicate IDs before a SOQL query.
  • Do not rely on Set or Map iteration order for business ordering. Sort an appropriate List when order matters.
  • Check for null keys and values where they are possible.
  • Check whether a Map contains a key when a null value could be ambiguous.
  • Avoid querying or performing DML inside loops.
  • Do not mutate a collection in a way that invalidates the loop currently iterating over it.
  • Choose collection element types precisely, such as List<Account> rather than an untyped collection where possible.
  • Remember that collection operations still consume CPU and heap; a Map is not a substitute for sensible data-volume design.

10. Collections and SOQL

SOQL commonly returns a List of sObjects. You can pass a Set of IDs into a bind expression using IN, and you can construct a Map from a List of queried sObjects.

Set<Id> accountIds = new Set<Id>();

// Populate accountIds from business logic...

List<Contact> contacts = [
    SELECT Id, Name, AccountId
    FROM Contact
    WHERE AccountId IN :accountIds
];

Map<Id, Contact> contactsById =
    new Map<Id, Contact>(contacts);

SOQL bind variables help keep values separate from query text. Always consider query selectivity, returned row volume, field requirements and sharing/security behavior.

Key takeaway

Lists preserve a sequence and allow duplicates, Sets store unique values, and Maps connect keys to values for efficient lookup. In Salesforce development, combining these collections is fundamental to bulk-safe triggers, efficient SOQL patterns, data transformation and integration processing. Choose the structure that matches the problem, then test it with realistic volumes and edge cases.

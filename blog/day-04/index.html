SALESFORCE ENGINEERING JOURNEY · DAY 04

Salesforce Security Model: Profiles, Permission Sets, Roles & Sharing

A practical guide to controlling who can access Salesforce functionality, objects, fields and individual records—and how to enforce those rules in Apex and Lightning Web Components.

Intermediate18–22 min readUpdated: November 2026

Salesforce security is not a single setting. It is a layered access model that determines what a user can do, which data they can access, and which fields they can view or change.

Imagine a manufacturing organization with sales representatives, regional managers, service agents and integration users. A sales representative may need to create and update opportunities but should not see every region's pipeline. A service agent may need access to cases and selected customer information, but not sensitive commercial fields. An integration user may need narrowly scoped API access to a defined set of objects.

These requirements cannot be solved by assigning profiles alone. A well-designed security model combines user permissions, object permissions, field-level security, record-level sharing, and secure application code.

Core principle: Grant the minimum access required to perform a job, then expand access deliberately. Security should be designed around business roles and data sensitivity—not around convenience or a one-size-fits-all administrator profile.

1. Understand the four access layers

A useful way to reason about Salesforce access is to separate it into four questions:

LayerQuestion answeredPrimary controls
Org / user accessCan the user log in and use a capability?User status, license, profile, user permissions, login and session controls
Object-level accessCan the user work with this type of record?Object permissions such as Read, Create, Edit and Delete
Field-level accessCan the user see or edit this particular field?Field-Level Security (FLS)
Record-level accessWhich individual records can the user access?OWD, role hierarchy, sharing rules, teams, manual and Apex-managed sharing

These controls work together. For example, a user can have Read permission on the Opportunity object but still be unable to see a particular Opportunity because record-level sharing does not grant access. A user can have access to an Account record but not be able to view its confidential margin field because FLS blocks that field.

Remember: Object permissions and FLS define what a user can do with an object and its fields. Record sharing defines which records the user can access. A record-sharing rule does not grant missing object or field permissions.

2. Profiles: the user's baseline

Every Salesforce user has exactly one profile. A profile provides a baseline of settings and permissions, including login hours, IP ranges (where configured), assigned apps, record type availability, page layout assignments, object permissions, field permissions and system permissions.

Profiles are not the same as roles. A profile answers what capabilities and object/field permissions a user has. A role primarily contributes to record-level access through the role hierarchy.

Example: A Sales User profile might provide Read, Create and Edit access to Accounts and Opportunities, while a Service User profile provides access to Cases and relevant customer objects. These are starting points, not a reason to create a new profile for every small variation in access.

3. Permission Sets and Permission Set Groups

Permission Sets

A permission set grants additional permissions to a user without changing the user's profile. A user can have multiple permission sets, making it easier to grant access based on responsibilities, projects or capabilities.

For example, a sales representative might receive a base Sales profile and separate permission sets for Export Reports, Manage Territory Data or Use a Pricing Application. Access can be added when the user needs it and removed when the responsibility ends.

Permission Set Groups

A permission set group bundles multiple permission sets so that administrators can assign a job-based collection of capabilities as one unit. For example, a Service Console User group could bundle Case Management, Knowledge Access and Omni-Channel Agent permissions.

Muting Permission Sets

A muting permission set can mute selected permissions that come from permission sets inside a permission set group. It does not revoke permissions granted independently by the user's profile or by another permission set outside that group. This distinction matters when troubleshooting why a user still has access.

FeaturePurposeTypical use
ProfileRequired baseline for each userCommon defaults and baseline permissions
Permission SetAdds specific permissionsTemporary or specialized capability
Permission Set GroupBundles permission setsJob function or persona-based access
Muting Permission SetMutes selected permissions within a groupFine-tuning a bundled permission model

Recommended direction: Keep profiles relatively minimal and use permission sets and permission set groups to manage most permission assignments. This reduces profile proliferation and makes access easier to audit.

4. Object-Level Security (CRUD)

Object permissions control whether users can perform actions on an object. The common permissions are:

  • Read: view records of the object, subject to record-level access.
  • Create: create new records.
  • Edit: update records the user can access.
  • Delete: delete records the user is authorized to delete.
  • View All: view all records of the object, overriding record-level sharing for that object.
  • Modify All: view, edit, delete and otherwise manage all records of the object, overriding record-level sharing for that object.

There are also broader system permissions such as View All Data and Modify All Data. These grant very broad access across the org and should be restricted to users with a genuine administrative requirement.

Do not confuse object access with record access. Granting Edit on Opportunity does not mean the user can edit every Opportunity. The user must also have access to the particular record, and the fields being changed must be editable.

5. Field-Level Security (FLS)

FLS controls whether a user can read or edit a specific field. It is especially important for sensitive information such as discount approvals, margin, personal information, health-related details or confidential account attributes.

For example, a sales representative may need to see Opportunity Amount and Stage but should not see an internal Margin Percentage field. A sales manager may be allowed to read that field, while a finance persona may also be allowed to update it.

  • Read access: the field can be viewed where it is otherwise displayed or queried.
  • Edit access: the field can be changed, subject to other access and business rules.

Use FLS rather than relying only on page layouts to protect sensitive data. Page layouts control the user interface; they are not a security boundary. A field hidden from a page layout can still be accessible through reports, APIs, exports or custom code if FLS allows it.

6. Record-Level Security: OWD, Roles and Sharing

Once a user has object permission, Salesforce still needs to determine which individual records that user can access. This is the purpose of record-level security.

Organization-Wide Defaults (OWD)

OWD establishes the baseline record access that users have to records they do not own. For many objects, common settings include Private, Public Read Only and Public Read/Write. Some objects support additional options such as Controlled by Parent or object-specific access levels.

Start with the most restrictive baseline that meets the business requirement, then open access through appropriate sharing mechanisms. Internal and external default access can be configured separately for supported objects.

OWD settingTypical meaning
PrivateUsers generally access records they own or records shared with them, plus access from applicable hierarchy and elevated permissions.
Public Read OnlyUsers can generally view records, but need ownership, sharing or elevated access to edit them.
Public Read/WriteUsers generally can view and edit records, subject to object permissions and other controls.
Controlled by ParentAccess to the child is determined by access to its parent, for supported relationships and objects.

OWD is a baseline—not a deny rule that later sharing features can tighten. Role hierarchy, sharing rules and other sharing mechanisms generally extend access beyond the baseline. If a user has broad permissions such as View All or Modify All, those can override record-level sharing for the applicable scope.

Role Hierarchy

The role hierarchy opens record access upward. Users higher in the hierarchy can generally access records owned by or shared with users below them. It is designed to support data visibility and management reporting, not to reproduce every title in the company's organization chart.

Example: A Regional Sales Manager role sits above Sales Representative roles. With the applicable hierarchy behavior, the manager can access records owned by representatives below them without a separate sharing rule for every representative.

For custom objects, the Grant Access Using Hierarchies option can be disabled where appropriate. Standard objects generally have hierarchy access behavior that cannot be disabled in the same way. Review the object-specific rules before relying on this setting.

Public Groups

A public group is a collection of users, roles, roles and subordinates, or other groups. Public groups are commonly used as the target of sharing rules and manual sharing. They help administrators define reusable access audiences.

Sharing Rules

Sharing rules automatically extend record access to users who do not own the records. They are commonly based on record ownership or record criteria and can share records with roles, roles and subordinates, or public groups.

Example: All Opportunities where Region equals East can be shared Read Only with the East Sales Leadership public group. A separate owner-based rule could share records owned by the Partner Sales role with the Partner Operations group.

Sharing rules open access; they do not make OWD more restrictive. Use the minimum access level required—Read Only or Read/Write.

Manual Sharing

Manual sharing allows a record owner, or another user with appropriate authority, to share an individual record with a user, role or group. It is useful for exceptions that do not fit a repeatable sharing rule. It is not a substitute for a scalable sharing design when the same access pattern applies to many records.

Teams and Territory Management

Account Teams, Opportunity Teams and Case Teams allow record-level collaboration with specific team members and access levels. Enterprise Territory Management supports access and account coverage based on sales territories. Choose these features when the business process is genuinely team- or territory-driven.

Apex Managed Sharing

When declarative sharing cannot represent a custom access requirement, Apex managed sharing can create or remove programmatic shares for supported custom objects. Share rows are stored in the object's share table, such as Project__Share, and include the parent record, user or group, access level and row cause.

// Illustrative example for a custom object with
// a custom Apex Sharing Reason named Project_Access__c
Project__Share shareRow = new Project__Share();
shareRow.ParentId = projectRecordId;
shareRow.UserOrGroupId = targetUserOrGroupId;
shareRow.AccessLevel = 'Read';
shareRow.RowCause = Schema.Project__Share.RowCause.Project_Access__c;
insert shareRow;

Custom Apex Sharing Reasons are available for custom objects. Standard objects have their own supported sharing mechanisms and do not support custom Apex Sharing Reasons in the same way. Design for owner changes, share recalculation, duplicate shares, revocation and bulk processing. Do not hard-code user IDs or create one-off sharing logic without a clear lifecycle.

7. Restriction Rules and Scoping Rules

These two features are easy to confuse:

  • Restriction Rules further limit the records that selected users can see, even when the sharing model would otherwise grant access, for supported objects and use cases.
  • Scoping Rules help users focus on a relevant subset of records in supported experiences. They do not revoke the user's underlying record access; users can still access records granted by the sharing model through other routes.

Use restriction rules when the requirement is to narrow visibility. Use scoping rules to improve relevance and focus—not as a security control.

8. How the access layers work together: a real-world scenario

Consider a manufacturing company with Sales Representatives, Regional Managers, Service Agents and Finance users.

PersonaObject and field permissionsRecord access design
Sales RepresentativeCreate, Read and Edit Accounts and Opportunities; no access to confidential margin fieldsPrivate Opportunities; own records and appropriate team access
Regional ManagerRead and Edit Opportunities; read selected margin fieldsRole above representatives; access to regional records via hierarchy and targeted sharing
Service AgentRead customer details and create/update Cases; no access to sensitive commercial fields unless requiredCase ownership, queues, teams and account-related access as designed
Finance AnalystRead financial fields and relevant objects; update approved finance fields onlyAccess to required accounts and opportunities through targeted sharing or a controlled finance dataset

The implementation sequence is important: define personas and data sensitivity; establish object and field permissions; set conservative OWD; create roles and groups; then add sharing rules, teams or Apex-managed sharing only where needed. Finally, test the model with actual users and representative records.

9. Enforcing security in Apex

Declarative permissions are not enough if custom Apex exposes data. Apex code must be designed to respect the intended access model. The exact default execution behavior is API-version dependent: Salesforce documents a change in API version 67.0, where Apex runs in user context by default, while API version 66.0 and earlier use system mode by default for object and field permissions. Make access modes explicit so that code remains understandable across versions.

Record-level sharing: with sharing, without sharing and inherited sharing

  • with sharing enforces the current user's record-sharing rules.
  • without sharing bypasses record-sharing rules and should be used only for a justified, controlled system-level operation.
  • inherited sharing adopts the caller's sharing context and is useful for service classes designed to run in different contexts.

These keywords address record-level sharing. They do not, by themselves, enforce object permissions or FLS. Salesforce recommends making the sharing declaration explicit on Apex classes that query or manipulate data.

Use user-mode SOQL and DML

For user-facing operations, user mode is a strong way to enforce the running user's sharing, object permissions and FLS at the database operation. For example:

public with sharing class OpportunityController {
    @AuraEnabled(cacheable=true)
    public static List<Opportunity> getMyOpportunities() {
        return [
            SELECT Id, Name, StageName, Amount
            FROM Opportunity
            WHERE OwnerId = :UserInfo.getUserId()
            WITH USER_MODE
            ORDER BY CreatedDate DESC
            LIMIT 100
        ];
    }
}

For DML, specify user mode when the operation should respect the user's access:

Database.SaveResult result = Database.insert(
    newCase,
    AccessLevel.USER_MODE
);

Use system mode only when the business requirement genuinely calls for elevated access. Document why elevation is necessary, minimize the data returned, validate inputs, and avoid exposing privileged results to callers who should not see them. A system-mode operation is not automatically safe just because the Apex class is declared with sharing.

Use Security.stripInaccessible()

Security.stripInaccessible() removes fields and relationship fields the user cannot access from sObjects. It can be used to sanitize records before DML, handle data from untrusted clients, or return a reduced field set instead of failing an entire operation. It does not replace record-level sharing; combine it with an appropriate sharing and data-access strategy.

List<Account> incomingAccounts = new List<Account>{
    new Account(
        Name = 'Northwind Manufacturing',
        AnnualRevenue = 5000000
    )
};

SObjectAccessDecision decision =
    Security.stripInaccessible(
        AccessType.CREATABLE,
        incomingAccounts
    );

List<SObject> safeRecords = decision.getRecords();
insert safeRecords;

In production code, consider the access mode of the subsequent DML operation as well, handle errors, and decide whether stripped fields should be logged or reported to the caller. The example illustrates field/object sanitization; it is not a complete input-validation or error-handling pattern.

Describe checks: a useful lower-level option

Describe methods such as isAccessible(), isCreateable() and isUpdateable() can be used to check object and field permissions explicitly. They remain useful for conditional behavior and legacy code, but user-mode database operations and stripInaccessible() can reduce repetitive security boilerplate in many scenarios.

Important distinction: with sharing is not the same as CRUD/FLS enforcement. A secure Apex endpoint needs a deliberate strategy for record access, object access, field access, input validation and output filtering.

10. LWC and API security considerations

  • Prefer Lightning Data Service (LDS) and UI API for standard record forms and data access where they meet the requirement. They handle sharing, CRUD and FLS for supported operations.
  • Secure Apex controllers exposed through @AuraEnabled. Use an explicit sharing declaration and user-mode database operations where the operation should reflect the current user's access.
  • Protect Apex class access. A user needs access to the Apex class through their profile or an assigned permission set to invoke an exposed method.
  • Validate all client input. Client-side validation improves usability but is not a security boundary. Validate IDs, allowed values, record relationships and business rules on the server.
  • Return only required fields. Avoid returning entire sObjects or sensitive data when the UI needs only a small response DTO.
  • Secure integrations. Use least-privilege integration users, appropriate OAuth scopes, Named Credentials and External Credentials where applicable. Do not embed secrets in LWC JavaScript, URLs or source code.
  • Review guest and external-user access carefully. Public site and guest-user access should be deliberately limited; never assume internal sharing behavior is appropriate for external users.

11. Common security mistakes

  • Assuming a profile or permission set controls which individual records a user can see.
  • Using roles to grant object permissions instead of using profiles and permission sets.
  • Assuming page layouts hide sensitive fields from APIs, reports or custom code.
  • Giving users View All Data or Modify All Data to solve a narrow record-sharing issue.
  • Using Public Read/Write OWD when a targeted sharing rule would meet the requirement.
  • Assuming with sharing automatically enforces CRUD and FLS.
  • Using without sharing without documenting why elevated access is required.
  • Trusting client-side checks or LWC visibility conditions as the only security enforcement.
  • Using scoping rules as if they restricted data access.
  • Failing to retest access after permission-set, role, ownership or sharing changes.

12. A practical security design and testing checklist

  1. Identify user personas, business responsibilities and integration identities.
  2. Classify sensitive objects and fields, including personal, financial and regulated information.
  3. Define the minimum object permissions required for each persona.
  4. Define field-level read and edit requirements independently of page layouts.
  5. Choose conservative OWD settings for each relevant object.
  6. Design roles around record visibility needs, not just job titles.
  7. Use public groups, sharing rules, teams and territories for repeatable access patterns.
  8. Use manual sharing for genuine exceptions and Apex managed sharing only when declarative tools are insufficient.
  9. Review system permissions such as View All, Modify All, View All Data and Modify All Data.
  10. Audit Apex, Flow, LWC, API and integration paths for security enforcement and privileged execution.
  11. Test positive and negative cases: users who should see records, users who should not, fields they can read, and fields they must not update.
  12. Retest after ownership changes, role changes, permission changes, deployments and new integrations.

Use representative test users—not only System Administrator—to validate the design. A security model is not complete until you have demonstrated both the access that must work and the access that must fail.

Key takeaway

Salesforce security is the combined result of user permissions, object permissions, field-level security and record-level sharing. Profiles and permission sets define capabilities; roles and sharing mechanisms influence record visibility; and Apex, LWC and integration code must preserve those boundaries. The strongest design starts restrictive, grants access intentionally and is validated with real user personas and negative tests.

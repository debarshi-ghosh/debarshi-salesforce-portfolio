Apex Programming: Classes, Objects, Methods and Constructors

A practical guide to Apex classes, objects, methods, constructors, access modifiers, static members, interfaces and testable Salesforce code.

Intermediate18–22 min readUpdated: November 2026

Apex is Salesforce's strongly typed, object-oriented programming language. It allows developers to execute business logic on the Salesforce Platform, interact with records, expose services and build reusable application behavior.

Knowing syntax is only the beginning. Good Apex design depends on understanding how classes are structured, how objects are created, how methods communicate and how constructors establish valid object state.

In this article: We move from programming fundamentals into the structure of Apex code: classes, instances, fields, properties, methods, constructors, access modifiers, static members, interfaces and practical design.

1. Where Apex fits

Apex runs on Salesforce's server-side platform and is commonly used in triggers, controllers, services, asynchronous jobs, integrations and invocable actions. Apex works with Salesforce data through sObjects and platform APIs, while sharing and data access security must be considered explicitly.

Apex is strongly typed and object-oriented. The compiler checks types, access and many syntax errors before code is deployed. Apex supports classes, interfaces, inheritance, exceptions, generics and collections, with platform-specific execution and governor limits.

2. Anatomy of an Apex class

A class is a blueprint that groups related data and behavior. A class can contain fields, properties, constructors, methods, inner classes and static initialization logic.

public class ServiceRequest {
    // Instance fields
    private String requestNumber;
    private String requestType;
    private Boolean urgent;

    // Constructor
    public ServiceRequest(
        String requestNumber,
        String requestType,
        Boolean urgent
    ) {
        this.requestNumber = requestNumber;
        this.requestType = requestType;
        this.urgent = urgent;
    }

    // Instance method
    public String getSummary() {
        return requestNumber + ' - ' + requestType;
    }
}

The class declaration defines the type. The fields store per-object state. The constructor initializes that state, and the method exposes behavior.

3. Objects and instances

An object is an instance of a class. Use the new keyword to invoke a constructor and create an instance.

ServiceRequest requestA =
    new ServiceRequest('SR-1001', 'Installation', false);

ServiceRequest requestB =
    new ServiceRequest('SR-1002', 'Repair', true);

System.debug(requestA.getSummary());
System.debug(requestB.getSummary());

Each instance has its own instance fields. Changing the state of one instance does not automatically change another instance of the same class.

Class vs. object vs. sObject

ConceptMeaningExample
ClassBlueprint defining state and behaviorServiceRequest
Object / instanceRuntime instance of a classnew ServiceRequest(...)
sObjectApex representation of a Salesforce recordAccount, Case, Opportunity

An sObject is also an object in the programming sense, but it represents a Salesforce data record and participates in platform data operations. A custom Apex class is not automatically a database object.

4. Fields and properties

Fields hold values. Properties provide a controlled way to expose values through getters and setters.

public class CustomerProfile {
    private String emailAddress;

    public String EmailAddress {
        get {
            return emailAddress;
        }
        set {
            if (value != null && value.contains('@')) {
                emailAddress = value;
            }
        }
    }
}

In Apex, value refers to the value being assigned in a property setter. Property accessors can be used to encapsulate validation or expose read-only state.

5. Methods: define behavior

A method is a named block of code. Its signature includes the method name, parameter types and return type (or void). Methods can be instance methods or static methods.

public class DiscountService {
    public Decimal calculateDiscount(
        Decimal amount,
        Decimal rate
    ) {
        if (amount == null || rate == null) {
            throw new IllegalArgumentException('Inputs are required');
        }
        if (amount < 0 || rate < 0 || rate > 1) {
            throw new IllegalArgumentException('Invalid amount or rate');
        }
        return amount * rate;
    }
}

Parameters and return values

  • Parameters are values passed by the caller.
  • The return type defines the value returned to the caller.
  • void means the method does not return a value.
  • A method should have a focused responsibility and a clear contract.

Method overloading

Apex supports method overloading: methods in the same class can share a name when their parameter lists differ.

public class GreetingService {
    public String greet(String name) {
        return 'Hello ' + name;
    }

    public String greet(String firstName, String lastName) {
        return 'Hello ' + firstName + ' ' + lastName;
    }
}

Changing only the return type is not enough to overload a method; the parameter list must differ.

6. Constructors: initialize object state

A constructor runs when an object is created using new. It has the same name as the class and no return type. Constructors are useful for ensuring an object starts in a valid state.

public class WorkOrderRequest {
    public String accountId;
    public String priority;
    public Date requestedDate;

    // No-argument constructor
    public WorkOrderRequest() {
        priority = 'Normal';
        requestedDate = Date.today();
    }

    // Parameterized constructor
    public WorkOrderRequest(
        String accountId,
        String priority
    ) {
        this.accountId = accountId;
        this.priority = priority;
        this.requestedDate = Date.today();
    }
}

Apex does not provide an implicit no-argument constructor once you define a constructor yourself. If callers need both forms, explicitly define both.

Constructor overloading and chaining

You can provide multiple constructors with different parameter lists. Use this(...) as the first statement in a constructor to call another constructor in the same class, where appropriate.

public class ContactRequest {
    public String lastName;
    public String source;

    public ContactRequest(String lastName) {
        this(lastName, 'Web');
    }

    public ContactRequest(String lastName, String source) {
        this.lastName = lastName;
        this.source = source;
    }
}

7. Access modifiers and visibility

Access modifiers control where a class member can be accessed. Select the narrowest visibility that supports the intended design.

ModifierMeaningTypical use
privateAccessible only within the declaring classInternal state and helper methods
protectedAccessible within the class and supported subclasses / namespace contextsExtension points for inheritance
publicAccessible to other Apex code in the namespaceApplication-level APIs
globalBroadest visibility across namespacesPublicly exposed package or platform APIs when required

Do not use global by default. It creates a broader contract that can be difficult to change, particularly in managed packages.

8. Static vs. instance members

Instance members belong to an object instance. Static members belong to the class itself and are accessed using the class name.

public class CurrencyRules {
    public static final String DEFAULT_CURRENCY = 'INR';

    public static Decimal roundToTwoPlaces(Decimal amount) {
        return amount == null ? null : amount.setScale(2);
    }
}

// Call static method without creating an instance
Decimal rounded = CurrencyRules.roundToTwoPlaces(125.567);

Static methods cannot directly access instance fields because they do not run against a particular object. Use static members for stateless utilities or class-level constants, not as a substitute for thoughtful object design.

9. Interfaces and abstract classes

An interface defines a contract that implementing classes must fulfill. It is useful when multiple implementations should be interchangeable.

public interface AssignmentStrategy {
    Id selectOwner(Id accountId);
}

public class DefaultAssignmentStrategy
    implements AssignmentStrategy {

    public Id selectOwner(Id accountId) {
        // Illustrative implementation
        return UserInfo.getUserId();
    }
}

An abstract class can provide shared state or implementation while requiring subclasses to implement abstract methods. A class can implement multiple interfaces, while Apex class inheritance is single inheritance.

10. Inner classes and DTOs

Inner classes are classes declared inside another class. They are useful for grouping types that are closely related, such as request and response structures for an integration or invocable action.

public class OrderSubmissionService {
    public class Request {
        public String externalOrderId;
        public Decimal amount;
    }

    public class Response {
        public Boolean success;
        public String message;
    }
}

DTOs (Data Transfer Objects) carry data between layers or across API boundaries. Keep them focused on the data contract rather than embedding unrelated business behavior.

11. Applying Apex class design in a real project

Imagine a manufacturing Salesforce org that receives installation requests. A maintainable design might separate responsibilities:

ComponentResponsibility
InstallationRequestRepresents request data and its invariants
InstallationPricingServiceCalculates charges and discounts
InstallationRepositoryEncapsulates record retrieval and persistence where useful
InstallationNotificationServiceCoordinates notification behavior
InstallationControllerExposes a focused interface to an LWC or supported UI entry point

This is an illustrative separation, not a mandatory class-per-concept rule. Avoid unnecessary abstraction for trivial functionality. Keep the architecture proportional to the complexity and reuse requirements.

12. Testing Apex classes

Unit tests should verify outcomes and important edge cases. Test public behavior rather than private implementation details.

@IsTest
private class DiscountServiceTest {
    @IsTest
    static void calculatesDiscount() {
        DiscountService service = new DiscountService();
        Decimal result = service.calculateDiscount(1000, 0.10);
        System.assertEquals(100, result);
    }

    @IsTest
    static void rejectsInvalidRate() {
        DiscountService service = new DiscountService();
        try {
            service.calculateDiscount(1000, 1.5);
            System.assert(false, 'Expected invalid rate exception');
        } catch (IllegalArgumentException ex) {
            System.assert(ex.getMessage().contains('Invalid'));
        }
    }
}

Also test null inputs, boundary values, expected exceptions and interactions with Salesforce data when the class performs queries or DML. Use dependency injection and interfaces when they make external dependencies easier to isolate.

13. Common mistakes

  • Creating one giant class that handles unrelated responsibilities.
  • Making every field and method public without a reason.
  • Forgetting to define a no-argument constructor when it is needed after adding a custom constructor.
  • Using static state to share mutable data between unrelated operations.
  • Writing methods with unclear names or too many parameters.
  • Using inheritance where composition would be simpler.
  • Exposing global APIs unnecessarily.
  • Writing tests that assert only code coverage rather than behavior.
  • Mixing UI, data access, business logic and integration concerns in one class.

  3. Create a method that calculates warranty eligibility from purchase date and warranty duration.

Key takeaway

Classes organize code, objects represent instances, methods define behavior and constructors establish valid state. Use access modifiers deliberately, keep responsibilities focused, prefer composition where it improves flexibility and write tests that prove behavior. These foundations prepare you to work confidently with Apex collections, triggers, services, integrations and asynchronous processing.

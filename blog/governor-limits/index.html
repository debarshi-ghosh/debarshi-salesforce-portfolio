Salesforce Governor Limits

A practical developer reference to transaction limits, asynchronous execution, platform allocations, common errors and how to monitor resource consumption.

Developer Reference15–20 min readReviewed: November 2026

Salesforce governor limits are runtime guardrails that help protect shared platform resources in a multi-tenant environment. They influence how we write Apex, design automation, query data, process integrations and scale applications.

Scope and freshness: This guide focuses on developer-critical limits, not every allocation in every Salesforce product. Numbers below are common documented Apex limits; edition-, feature-, namespace- and context-specific exceptions exist. Always verify limits against Salesforce's current Developer Limits and Allocations Quick Reference and Execution Governors and Limits before using them in production decisions.

1. Governor limits vs allocations

  • Per-transaction governor limits: apply to an individual transaction and are reset when a new transaction starts. Batch Apex limits reset for each execute() chunk.
  • Org-wide or rolling allocations: measure consumption across a period or across the org, such as daily asynchronous Apex executions or API requests.
  • Feature limits: apply to specific capabilities, objects, automation, or editions.
  • Static and size limits: constrain code size, payloads, or other resources.

Do not assume that every Salesforce limit is a per-transaction Apex governor limit. The right troubleshooting approach depends on which category was exceeded.

3. SOQL, SOSL and data access

What to remember

  • Normal SOQL query results are subject to the 50,000-row transaction limit.
  • Database.getQueryLocator() can return up to 10,000 records outside Batch Apex; in Batch Apex, a QueryLocator can support up to 50 million records.
  • SOQL OFFSET has a maximum offset of 2,000 rows; use keyset pagination or another suitable strategy for deeper paging.
  • Query selectivity matters for large data volumes even when the query does not hit a numeric governor limit.
  • Relationship queries, aggregate queries, and query plan behavior have additional considerations; consult the SOQL reference for the specific feature.

Bad pattern

for (Account a : accounts) {
    List contacts = [
        SELECT Id FROM Contact WHERE AccountId = :a.Id
    ];
}

Bulkified approach

Set<Id> accountIds = new Map<Id, Account>(accounts).keySet();
Map<Id, List<Contact>> contactsByAccount = new Map<Id, List<Contact>>();

for (Contact c : [
    SELECT Id, AccountId FROM Contact
    WHERE AccountId IN :accountIds
]) {
    if (!contactsByAccount.containsKey(c.AccountId)) {
        contactsByAccount.put(c.AccountId, new List<Contact>());
    }
    contactsByAccount.get(c.AccountId).add(c);
}

4. DML and transaction limits

DML statements and DML rows are separate counters. One bulk update of 200 records consumes one DML statement but processes 200 rows. Repeating DML in a loop can exhaust the statement limit quickly.

  • Prefer collection-based insert, update, upsert, and delete.
  • Use Database methods with allOrNone=false when partial success is an intentional requirement; inspect each SaveResult.
  • Remember that triggers and declarative automation invoked by DML consume resources in the transaction too.
  • Use savepoints and rollback deliberately; they do not create a new governor-limit context.

5. CPU time and heap

CPU time measures Salesforce application-server processing. SOQL/DML database execution time and time waiting for callouts are not counted as Apex CPU time, although returned data and subsequent processing can increase CPU and heap consumption.

Heap is memory used by objects, collections, strings and payloads in the transaction. Large queried result sets, deeply nested collections, JSON deserialization and retaining unnecessary references can cause heap errors.

Typical CPU error: Apex CPU time limit exceeded. Look for nested loops, repeated work, expensive formula/automation interactions, inefficient trigger logic and managed-package code contributing to the same transaction.

6. Callout limits

  • Maximum 100 callouts per transaction.
  • Maximum cumulative callout timeout is 120 seconds per transaction.
  • Callout request and response size limits also apply; check the current Apex reference for payload constraints.
  • Do not make one callout per record in a large trigger batch. Aggregate requests or use a designed asynchronous integration pattern.
  • For callouts from record-triggered contexts, consider Queueable Apex or another supported async pattern when transaction constraints require it.

Batch Apex is useful for large data volumes because each execute() chunk runs as a separate transaction with fresh per-transaction limits. The default batch scope is 200; tune it based on processing complexity, heap, CPU and downstream automation—not merely the maximum possible scope.

  • Queueable Apex: one child Queueable can be enqueued from an executing Queueable; design chains and orchestration intentionally.
  • Future methods: legacy asynchronous mechanism with restrictions; Queueable is generally preferred for new work.
  • Scheduled Apex: schedules execution but does not automatically grant asynchronous governor limits to the scheduled code.

8. API limits and org allocations

API request allocations are org-level and depend on edition, licenses and purchased capacity. They are not the same as the per-transaction SOQL/DML limits of Apex.

  • Monitor API usage and the applicable daily allocation in Setup and through the REST API limits resource.
  • Use Bulk API for large data operations instead of sending huge volumes of individual REST requests.
  • Handle REQUEST_LIMIT_EXCEEDED with backoff, workload planning and allocation monitoring; do not retry aggressively without delay.
  • Concurrent API requests and long-running request restrictions are separate from daily API allocations.

9. Flow and automation limits

Flow does not have an independent unlimited database budget. When Flow runs in a transaction with Apex or other automation, applicable transaction resources are shared.

  • Bulkify record-triggered Flows: operate on collections and avoid per-record Get Records or DML patterns when possible.
  • Understand Flow interview and element behavior, scheduled paths, paused interviews and per-org flow allocations.
  • Automation invoked by a save can contribute to CPU, SOQL, DML and other transaction consumption.
  • Flow-specific limits—such as interview size, active flows, versions and paused interviews—are documented separately and may depend on edition.

10. Other important limit families

Depending on your work, learn the relevant limits for:

  • Platform Events and Change Data Capture: publishing, event size, delivery allocations, subscribers and retention.
  • Email: per-transaction sendEmail invocations and org/day recipient allocations.
  • Apex code: per-class/trigger size, total org code size, method size and recursion/stack constraints.
  • Data and storage: object/field allocations, file size, storage capacity and relationship constraints.
  • Flow: versions, active flows, interview size and paused interviews.
  • Feature/edition allocations: rules, users, licenses, product-specific capacities and contractual restrictions.

These are not all interchangeable governor limits. Find the authoritative reference for the feature you are implementing.

11. Managed-package namespace limits

Certified managed packages can have namespace-specific governor-limit treatment for certain resources. This does not mean every limit is multiplied or that packages are isolated from all transaction resources. Cross-namespace interactions, shared limits and package certification rules are nuanced; verify the current Apex documentation before relying on namespace allowances.

12. Monitor limits with the Apex Limits class

The Limits class exposes current transaction consumption and applicable limits. It is useful in diagnostics, tests and carefully designed guard conditions.

System.debug('SOQL used: ' + Limits.getQueries());
System.debug('SOQL limit: ' + Limits.getLimitQueries());

System.debug('DML used: ' + Limits.getDmlStatements());
System.debug('DML limit: ' + Limits.getLimitDmlStatements());

System.debug('CPU used: ' + Limits.getCpuTime());
System.debug('CPU limit: ' + Limits.getLimitCpuTime());

System.debug('Heap used: ' + Limits.getHeapSize());
System.debug('Heap limit: ' + Limits.getLimitHeapSize());

For org-wide allocations, use the REST API /limits resource or Apex OrgLimits methods where supported. For operational monitoring, Salesforce Setup's Governor Limit Insights can surface trends and breaches for supported categories.

14. Developer best practices

  1. Bulkify triggers and Flow from the start.
  2. Never put SOQL or DML directly inside record loops.
  3. Query only required fields and records; design selective filters for large data volumes.
  4. Use Batch Apex for large-volume processing and Queueable for appropriately scoped async work.
  5. Keep collections and payloads small; avoid unnecessary object retention.
  6. Account for all automation and package code in a transaction—not just your class.
  7. Monitor usage with Limits methods and org-level allocation tools.
  8. Do not hardcode assumptions about allocations that can vary by edition or release.
  9. Read error messages and identify whether the limit is per transaction, org-wide or feature-specific.

15. What should a Salesforce developer memorize?

Core memory set: 100 SOQL / 200 async; 150 DML; 50,000 query rows; 10,000 DML rows; 10s sync CPU / 60s async CPU; 6 MB sync heap / 12 MB async heap; 100 callouts; 120s cumulative callout timeout. Know the context and where to verify the rest.

You do not need to memorize every feature allocation. You do need to recognize the categories, design within common limits, diagnose limit errors, and retrieve the authoritative current value quickly.

SALESFORCE ENGINEERING JOURNEY · DAY 05

Salesforce Flow vs Apex: Choosing the Right Automation Tool

A practical, architecture-first guide to selecting declarative automation, programmatic logic or a hybrid approach—based on complexity, automation density, performance and long-term maintainability.

Intermediate16–20 min readUpdated: November 2026

One of the most common design decisions in Salesforce development is whether a requirement should be implemented using Flow or Apex.

For example, when an Opportunity is marked Closed Won, the business may want to create an onboarding task, update a related Account, notify an operations team and create a downstream service record. All of this might be possible with Flow. But if the process grows to include complex calculations, large data volumes, sophisticated deduplication, reusable domain logic and intricate transaction handling, Apex may be the better foundation.

The right question is not simply, “Can Flow do this?” or “Can Apex do this?” Both tools can query records, apply conditions and perform data operations. The real question is: which design will be easiest to understand, govern, test, operate and scale over time?

Core principle: Choose the simplest tool that meets the functional and non-functional requirements. For record-triggered automation, assess automation density—not just the preference or skill set of the person building it.

1. Understand the tools

What is Salesforce Flow?

Flow is Salesforce's declarative automation and process-building tool. It lets admins and developers build logic visually in Flow Builder using elements, resources, decisions and connectors, with no Apex required for many common use cases.

Common Flow types include:

  • Screen Flow: guides a user through an interactive process, collects input and performs actions. It can be launched from record pages, actions, buttons, utility bars and other supported entry points.
  • Record-Triggered Flow: starts when a record is created, updated or deleted, depending on supported configuration. It is used for before-save updates, after-save actions and scheduled paths.
  • Schedule-Triggered Flow: runs on a defined schedule and selects records that meet configured criteria.
  • Autolaunched Flow: runs without screens and can be invoked by other automation or supported platform entry points.
  • Platform Event-Triggered Flow: starts when a platform event message is received.

What is Apex?

Apex is Salesforce's strongly typed, object-oriented programming language. It provides programmatic control over data access, business logic, transactions, error handling and reusable services.

Common automation entry points and patterns include:

  • Apex Triggers: execute before or after DML events on records.
  • Invocable Apex: exposes Apex methods to Flow and other supported automation tools.
  • Queueable, Batch and Scheduled Apex: support asynchronous and scheduled processing patterns.
  • Apex services and domain classes: encapsulate reusable business logic called by triggers, controllers, invocable actions or other Apex code.

3. When should you choose Flow?

Flow is usually a strong choice when the process is declarative, easy to express visually and likely to be maintained by admins or a mixed admin-developer team.

  • Simple field updates and straightforward cross-object updates.
  • Creating related records from a clear business event.
  • Sending notifications, emails or routing work to queues and users.
  • Guided user journeys such as intake, onboarding, service requests and data capture.
  • Scheduled follow-ups based on record dates or conditions.
  • Orchestrating a predictable process with decisions and reusable subflows.
  • Low-density record-triggered automation where the object has few independent automation paths and modest data volume.

Example: When a Case is created with Priority = High, set an escalation flag, assign it to a defined queue and notify the support lead. If the rules are simple and the object has a manageable automation footprint, a record-triggered Flow is usually a good fit.

Before-save vs after-save record-triggered Flow

Use a before-save record-triggered Flow when you only need to update fields on the record that triggered the Flow. This avoids a separate update operation and is generally more efficient for that narrow purpose.

Use an after-save Flow when you need to create or update related records, perform actions that require the record to be saved, send notifications or invoke other supported actions. Scheduled paths are useful when work must happen later relative to a record event and the scheduling behavior fits the requirement.

4. When should you choose Apex?

Apex becomes more appropriate when the requirement needs precise programmatic control, advanced data structures, sophisticated transaction handling or predictable performance at scale.

  • Complex calculations or algorithms that are awkward to express and maintain in Flow.
  • High-volume processing where collection-oriented query and DML strategies are essential.
  • Complex deduplication or expensive computations that should be reused within a transaction.
  • Advanced error handling, partial-success DML or savepoint and rollback behavior.
  • Reusable business logic shared by triggers, APIs, LWC controllers and invocable actions.
  • Complex integration orchestration, payload transformation or specialized callout behavior.
  • Scenarios where a well-designed trigger framework and service layer provide clearer governance than a large collection of automation paths.

Example: A nightly process recalculates allocation values across a large portfolio of Opportunities, applies multi-level rules, handles duplicate relationships, logs record-level failures and retries eligible records. Batch Apex or another suitable Apex processing pattern may provide the control required. The exact design still depends on volume, latency, locking and retry requirements.

5. The hybrid approach: Flow + Invocable Apex

Flow and Apex are not competing technologies that must be kept completely separate. A hybrid architecture can combine declarative orchestration with code for the parts that genuinely need it.

For example, a Screen Flow can collect user input, validate required answers and guide an operations user through a process. It can then call an Invocable Apex action to calculate a complex allocation, validate a large collection of records or create a structured integration payload.

The Flow remains responsible for the user journey and orchestration. Apex encapsulates the complex computation in a reusable, bulk-safe unit.

Illustrative Invocable Apex action

public with sharing class DiscountCalculatorAction {
    public class Request {
        @InvocableVariable(required=true)
        public Decimal amount;

        @InvocableVariable(required=true)
        public Decimal discountPercent;
    }

    public class Response {
        @InvocableVariable
        public Decimal finalAmount;
    }

    @InvocableMethod(
        label='Calculate Discounted Amount'
        description='Calculates the amount after discount'
    )
    public static List<Response> calculate(List<Request> requests) {
        List<Response> results = new List<Response>();

        for (Request requestItem : requests) {
            Response result = new Response();
            Decimal discount =
                requestItem.amount * requestItem.discountPercent / 100;
            result.finalAmount = requestItem.amount - discount;
            results.add(result);
        }

        return results;
    }
}

This example is intentionally small to demonstrate the Invocable Apex contract. A production implementation should validate nulls, numeric ranges, currency and rounding rules, define the appropriate sharing and CRUD/FLS behavior, and test bulk inputs and invalid requests.

6. A modern architecture lens: automation density

Salesforce's current Architect guidance for record-triggered automation introduces the idea of automation density. Instead of choosing Flow because the builder is an admin or Apex because the builder is a developer, assess the cumulative automation load on each object.

Three dimensions are especially important:

  1. Automation quantity: How many flows, trigger actions and other automation components execute during one DML event?
  2. Record volume: How many records are processed in a transaction, including API loads, integrations and batch operations?
  3. Dependency sprawl: How many downstream updates and related-object operations are triggered by the initial change?
Automation densityArchitectural directionWhy
LowRecord-Triggered FlowClear, relatively independent automation with modest volume and limited downstream dependencies.
MediumRecord-Triggered Flow with Invocable ApexFlow coordinates the process while Apex handles focused complex computation or data operations.
HighApex trigger architectureCentralized entry point, explicit ordering, bulk-safe processing and better control over complex dependencies.

This is an architectural heuristic, not a fixed numerical threshold. Evaluate the actual object workload, limits, transaction behavior, team capability and operational model. A low-density object may still need Apex for a specialized requirement, and a Flow may still be appropriate in parts of a larger Apex-led design.

Important design guidance: For a given Salesforce object, aim for one primary entry point into record-triggered automation. Avoid creating a fragmented design where multiple independent Flows and Apex triggers compete to coordinate the same business process. Use Flow Trigger Explorer and a documented execution strategy to make the automation understandable.

7. Example: designing Opportunity automation

Consider a manufacturing organization with the following requirement when an Opportunity is marked Closed Won:

  • Update a simple onboarding status on the Opportunity.
  • Create an onboarding record related to the Account and Opportunity.
  • Calculate a complex allocation across multiple product lines.
  • Notify the implementation team.
  • Support bulk updates from an ERP integration.

A possible design decision:

RequirementPossible implementationReason
Set a field on the triggering OpportunityBefore-save Flow, if the object architecture is Flow-ledSimple same-record update
Create a related onboarding recordAfter-save FlowDeclarative related-record creation
Complex allocation across product linesInvocable Apex or Apex serviceReusable, testable computation and collection handling
Notify the implementation teamFlow action or supported notification mechanismSimple orchestration step
Handle high-volume, dependency-heavy processingApex-led trigger/service design, if density warrants itCentralized orchestration and explicit bulk processing

The table illustrates possible components, not a recommendation to create separate entry points for each row. The architecture should first choose the object's primary record-triggered entry point, then delegate to subflows or Apex services in a controlled sequence.

8. Performance, bulkification and governor limits

Flow and Apex execute on the same Salesforce platform and are subject to transaction-level resource limits. Flow is not a way to avoid Apex governor limits. If an element causes the transaction to exceed an enforced limit, the transaction can roll back even when the element has a fault connector.

For either tool:

  • Design for batches and bulk operations, not only a single record edited in the UI.
  • Reduce unnecessary queries, DML operations and repeated updates.
  • Avoid automation that updates a record in a way that re-enters the same process without a clear recursion strategy.
  • Keep cross-object dependency chains short and intentional.
  • Use entry criteria so automation runs only when relevant fields or conditions change.
  • Test API and integration data loads as well as manual UI updates.
  • Monitor failures and transaction behavior in representative production-like volumes.

In Apex, query and update collections outside loops and use Maps and Sets to avoid repeated work. In Flow, use collection operations and avoid Get Records, Update Records or other database operations inside loops when the same work can be performed on a collection.

9. Error handling and observability

A production automation design must explain what happens when something fails.

Flow

  • Connect fault paths for elements that can fail and decide whether to show a useful message, log the failure or route it for support.
  • Use fault connectors thoughtfully; a fault path does not guarantee that the entire transaction can commit if a governor limit or other transaction-level failure occurs.
  • For important processes, capture context such as record ID, Flow name, failed element, error message and correlation identifier where appropriate.
  • Use Flow error emails and operational monitoring as part of a broader support process.

Apex

  • Handle expected exceptions and use partial-success DML methods where the business requirement allows individual record failures.
  • Use structured logs and correlation IDs for integration and asynchronous processing.
  • Do not swallow exceptions silently. Preserve enough context for support teams to diagnose and recover.
  • Design retries to be safe and idempotent; repeated execution should not create duplicate downstream records or side effects.

10. Maintainability and governance checklist

  1. Understand the business requirement and identify the record event or user journey that starts the process.
  2. Check whether a formula, validation rule or standard platform feature can meet the requirement before creating automation.
  3. Review all existing automation on the object before adding a new entry point.
  4. Assess automation quantity, record volume and dependency sprawl.
  5. Choose Flow, Apex or a hybrid approach based on the required behavior—not personal preference.
  6. Define one primary entry point for record-triggered automation on the object and document the sequence.
  7. Keep Flows focused, named consistently and decomposed into reusable subflows where appropriate.
  8. Keep Apex modular, bulk-safe, testable and aligned with a consistent trigger/service architecture.
  9. Enforce security in both declarative and programmatic paths.
  10. Test single-record, bulk, integration, recursion, fault and negative scenarios.
  11. Define monitoring, alerting, ownership and recovery procedures.
  12. Review the design whenever new automation is introduced on the same object.

11. Common mistakes to avoid

  • Choosing Flow or Apex based only on who is building the solution.
  • Building one enormous Flow that handles unrelated business processes.
  • Creating multiple independent record-triggered entry points on the same object without a clear orchestration strategy.
  • Using Apex for simple field updates that a before-save Flow can handle efficiently.
  • Using Flow for complex, high-volume processing that needs advanced collection handling and transaction control.
  • Calling Invocable Apex without designing for bulk input.
  • Putting database operations inside Flow or Apex loops unnecessarily.
  • Assuming asynchronous execution automatically solves performance or limit problems.
  • Adding fault paths but failing to define logging, notification and recovery behavior.
  • Failing to regression-test existing automation when a new process is added.

Key takeaway

Flow and Apex are complementary tools. Flow is excellent for transparent, declarative business processes; Apex is better suited to complex algorithms, high-volume processing and granular transaction control. For record-triggered automation, evaluate the cumulative automation density of the object and establish one clear entry point. A thoughtful hybrid design often gives the best balance of admin-friendly orchestration and developer-level control.

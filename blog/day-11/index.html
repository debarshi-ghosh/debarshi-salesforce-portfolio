Apex Triggers: Context Variables and Execution Lifecycle

Understand the difference between structured SOQL queries and text-based SOSL search, with Apex examples, decision guidance and practical use cases.

Intermediate15–20 min readUpdated: November 2026

1. Trigger execution model

Apex triggers execute within the transaction that performs the record operation. Before triggers can validate or modify incoming records without additional DML. After triggers can access system-assigned IDs and perform related-record work, but their context records are read-only. After does not mean committed: later automation or an exception can still roll back the transaction.

2. Context variable availability

After insertYesNoYesNo
Before/after updateYesYesYesYes

Trigger.new is writable only in before insert and before update. Trigger.old is always read-only. Trigger.size describes the current invocation, not the entire originating request. Trigger.operationType returns a System.TriggerOperation enum; isBefore, isAfter, isInsert, isUpdate, isDelete and isUndelete allow explicit routing.

3. Order of execution and transaction boundaries

Salesforce performs initial validation and before-save record-triggered flows before before triggers. Validation rules and duplicate checks precede provisional database saving and after triggers. Workflow field updates and other automation can cause additional update-trigger execution. The transaction commits only after synchronous processing succeeds; post-commit work executes separately. Do not assume a single trigger invocation per user action.

4. Practical example: change detection and validation

trigger AccountLifecycle on Account (before insert, before update) {
  for (Account a : Trigger.new) {
    if (Trigger.isInsert && String.isBlank(a.Description)) {
      a.Description = 'Pending review';
    }
    if (Trigger.isUpdate) {
      Account prior = Trigger.oldMap.get(a.Id);
      if (a.Name != prior.Name && String.isBlank(a.Name)) {
        a.Name.addError('Account name cannot be blank.');
      }
    }
  }
}

Use oldMap to compare prior and incoming values. addError rejects the affected record; whether other records succeed depends on the caller's all-or-none behavior. Never issue update DML on the same records in their before trigger.

5. Bulk and re-entry considerations

Trigger invocations process collections, commonly up to 200 records per batch. Design for repeated execution, shared governor limits and related automation. A static Boolean recursion guard can skip legitimate records in subsequent invocations. Prefer meaningful field-change checks and idempotent processing; where necessary track processed record IDs with a clearly defined transaction scope.

6. Testing strategy

Test insert, update, delete and undelete separately. Assert persisted outcomes, unchanged-field behavior, validation failures and bulk execution with 200 records. Use Test.startTest and Test.stopTest to isolate limits and exercise asynchronous work. Test partial-success DML explicitly with Database.update(records, false) where appropriate.

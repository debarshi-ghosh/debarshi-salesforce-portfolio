Apex Fundamentals: Build Your First Useful Class

Move from syntax to engineering habits: methods, collections, bulk processing and tests—using a small Account service.

Beginner-friendly8–10 min readUpdated: November 2026

In Day 1, we mapped the Salesforce developer journey. Today we begin practicing one of its core skills: writing Apex that is readable, bulk-safe and testable.

Goal: Understand the shape of an Apex class, pass data through methods, work with collections, perform bulk DML, and verify behavior with an Apex test.

1. What is a class and a method?

A class groups related behavior. A method is an operation that the class exposes or uses. Parameters let callers provide input; a return type describes the result.

public class GreetingService {
    public static String greet(String name) {
        return 'Hello, ' + name;
    }
}

public controls visibility, static means the method belongs to the class rather than an instance, and String is the return type. This method accepts one String and returns another.

2. Use collections to handle multiple records

Salesforce code often receives many records in one transaction. Learn these three collection types early:

  • List: ordered collection; duplicates are allowed.
  • Set: unique values.
  • Map: key-value lookup, useful for matching records by Id or another key.

Do not design a method that assumes it will receive only one record. Bulk behavior is a core Salesforce habit.

3. A small Account service

This example creates Accounts from a list of names. It validates inputs, builds records in memory, and performs one insert operation after the loop.

public with sharing class AccountCreationService {
    public static List<Account> createAccounts(List<String> names) {
        List<Account> accountsToInsert = new List<Account>();

        if (names == null || names.isEmpty()) {
            return accountsToInsert;
        }

        for (String name : names) {
            if (String.isBlank(name)) {
                continue;
            }
            accountsToInsert.add(new Account(Name = name.trim()));
        }

        if (!accountsToInsert.isEmpty()) {
            insert accountsToInsert;
        }

        return accountsToInsert;
    }
}

What to notice

  • with sharing declares that record-sharing rules should be respected for this class. It is not a replacement for object/field permission enforcement.
  • The method accepts a List<String>, not a single name.
  • Records are prepared inside the loop, but DML runs once outside it.
  • Null, empty and blank inputs are handled deliberately.
  • The method returns inserted records, including their generated Ids.
Important: This is a learning example, not a universal production service. In production, decide how to handle partial failures, CRUD/FLS enforcement, duplicate names, error reporting and caller expectations.

4. Write a test that checks behavior

A test should verify outcomes—not merely execute lines. Here we check that valid names create records, whitespace is trimmed, and blank entries are skipped.

@IsTest
private class AccountCreationServiceTest {
    @IsTest
    static void createsOnlyValidAccounts() {
        List<String> names = new List<String>{
            'Acme', '  Northwind  ', '', null
        };

        Test.startTest();
        List<Account> created =
            AccountCreationService.createAccounts(names);
        Test.stopTest();

        System.assertEquals(2, created.size());
        System.assertEquals('Acme', created[0].Name);
        System.assertEquals('Northwind', created[1].Name);
        System.assertNotEquals(null, created[0].Id);

        System.assertEquals(
            2,
            [SELECT COUNT() FROM Account
             WHERE Name IN ('Acme', 'Northwind')]
        );
    }

    @IsTest
    static void handlesNullInput() {
        List<Account> created =
            AccountCreationService.createAccounts(null);
        System.assertEquals(0, created.size());
    }
}

5. The engineering habits behind the example

  • Bulkify: process collections and keep SOQL/DML out of loops.
  • Separate responsibilities: keep a class focused on a clear job.
  • Make assumptions explicit: decide how invalid input and failures should behave.
  • Test edge cases: empty lists, nulls, blank values and expected record changes.
  • Keep security in view: sharing, CRUD and field-level security are different concerns.

6. Try it yourself

  1. Deploy the sample into a Developer Edition or Trailhead Playground.
  2. Add a test for an empty list.
  3. Change the service to return a count instead of records—what would the method signature become?
  4. Research how Database.insert(records, false) differs from plain insert.
  5. Consider how you would report each failed record to the caller.

Key takeaway

Good Apex is not just syntax that compiles. It is code that handles collections, respects platform behavior, makes its assumptions clear and proves its behavior through tests. Practice these habits from your first class.

SALESFORCE ENGINEERING JOURNEY · DAY 02

Understanding Salesforce Architecture

How the multi-tenant platform actually works—and why it shapes the way we build, secure and scale Salesforce applications.

Foundation10–12 min readUpdated: November 2026

Salesforce is often described as a cloud CRM, but understanding its architecture gives developers a much stronger mental model of the platform. It explains why metadata matters, why customers share infrastructure safely, why governor limits exist and what happens behind a seemingly simple record save.

In this article: We focus on the architecture concepts that every Salesforce developer should understand before moving deeper into data modeling, automation or Apex.

1. What does multi-tenant architecture mean?

In a traditional single-tenant approach, an organization may operate a dedicated application stack and database environment. Salesforce follows a multi-tenant model: many customer organizations (tenants) use a shared platform and common infrastructure, while their data and configuration remain logically separated.

Think of an apartment building. Residents share the building's structure and utilities, but each household has its own private space and access. In Salesforce, customers share platform resources and services; access controls and tenant-aware data handling keep one customer's records from becoming another customer's records.

  • Shared: platform software, infrastructure services and managed operational capabilities.
  • Tenant-specific: organization data, configuration, users, permissions and customizations.
  • Platform responsibility: enforce isolation, security and resource governance across organizations.

2. A simplified Salesforce architecture view

This is a conceptual model—not a literal deployment diagram or a claim about every internal Salesforce service.

      |

 (security, metadata, automation,

      |

      |
 Tenant-aware data + metadata
 (Org A | Org B | Org C ...)

Salesforce abstracts infrastructure management from customers. Developers work primarily with platform capabilities and metadata rather than provisioning application servers or managing database instances directly.

3. Metadata-driven architecture: configuration is part of the application

In Salesforce, metadata describes how an application behaves and is presented: objects, fields, relationships, validation rules, flows, layouts, Apex classes, Lightning components and much more.

When you create a custom object or field, you are not simply changing a database schema manually. You are defining metadata that the platform interprets and uses to provide application behavior.

  • Metadata: describes structure and behavior—such as a custom field, Flow or permission set.
  • Data: business records stored and managed through the platform—such as Accounts, Cases or custom-object records.
  • Runtime: platform services interpret metadata and execute requests, automation and application logic.
Developer takeaway: Metadata is deployable application source. Treat configuration changes with the same discipline as code: review, version, test and release them intentionally.

4. How does Salesforce isolate tenant data?

Salesforce uses tenant-aware data management and platform security to keep organizations logically separated. A developer interacts with records through supported platform interfaces—SOQL, DML, APIs and UI components—rather than directly querying shared physical storage.

Within a single organization, access is further controlled by Salesforce's security model: object permissions, field-level security, record sharing and other access policies. These controls answer different questions and should not be treated as interchangeable.

  • Organization boundaries provide tenant isolation.
  • CRUD and field-level security govern access to objects and fields.
  • Sharing controls which records a user can access.
  • Secure code must respect the relevant access controls; sharing alone does not enforce CRUD/FLS.

5. Shared resources and governor limits

Because Salesforce is multi-tenant, workloads must be governed so that one transaction or tenant cannot consume an unfair share of common resources. Governor limits are a visible part of that resource-governance model.

Examples developers encounter include limits on SOQL queries, DML statements, rows queried or processed, CPU time and heap size. Exact limits depend on execution context and can change, so consult the current Salesforce documentation rather than memorizing a single universal number.

These limits encourage designs that scale: bulk processing, selective queries, efficient data access, asynchronous work when appropriate, and avoiding repeated database operations inside loops.

6. What happens when you save a record?

A simplified record-save journey can help connect architecture to everyday development. Actual execution details vary by operation and platform feature.

  1. A user, API client or application submits a create/update request.
  2. The platform identifies the organization context and applies applicable access checks.
  3. It processes the transaction, including relevant validations and automation (such as triggers and record-triggered flows, according to execution order).
  4. The platform performs database work and evaluates transaction outcomes.
  5. On success, the transaction commits; on an unhandled failure, the transaction may roll back.
  6. The caller receives a result or error response.

This is why a record save can invoke much more than a single field update—and why understanding automation, transaction boundaries and error handling matters.

7. What this means for Salesforce developers

  • Build for shared resources: bulkify operations and design efficient queries.
  • Use platform abstractions: work through supported APIs and metadata rather than assuming direct infrastructure access.
  • Version metadata: keep configuration and code in source control.
  • Design security deliberately: consider org permissions, record sharing and application access separately.
  • Think transactionally: understand what runs during save, what can fail and what rolls back.
  • Test at realistic scale: single-record success is not enough to prove bulk behavior.

Key takeaway

Salesforce is a shared, metadata-driven platform that abstracts infrastructure while enforcing tenant isolation and resource governance. Once you understand this foundation, data modeling, security, automation and Apex design decisions become much easier to reason about.

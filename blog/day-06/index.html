SALESFORCE ENGINEERING JOURNEY · DAY 06

Programming Fundamentals: Think Logically, Design Clearly, Write Better Code

Build the core programming mindset behind maintainable Salesforce solutions—from problem decomposition and data types to methods, object-oriented design and clean code.

Beginner to intermediate18–22 min readUpdated: November 2026

Before learning Apex syntax, triggers or Lightning Web Components, it is important to understand the fundamentals that make any program work. Languages and frameworks change, but the ability to break down a problem, model data, control execution and organize responsibilities remains useful throughout a developer's career.

In Salesforce projects, these fundamentals appear every day: validating an Opportunity, calculating a discount, processing a collection of Accounts, coordinating service requests or designing a reusable integration service.

Core idea: Good programming is not about writing the maximum amount of code. It is about expressing the correct behavior clearly, safely and in a way that can be tested and maintained.

1. Start with problem solving, not code

Before opening the editor, make sure you understand the problem. A useful approach is to turn a business requirement into a sequence of explicit steps.

  1. Understand the expected outcome: What should happen, and for whom?
  2. Identify inputs: Which values or records are needed?
  3. Define rules: What conditions, calculations or validations apply?
  4. Identify outputs and side effects: What should be returned, created, updated or communicated?
  5. Consider edge cases: What if input is missing, duplicated, invalid or unexpectedly large?
  6. Write examples: Describe at least one normal case and one failure case.
  7. Choose the implementation: Only now decide which language features or Salesforce tools are appropriate.

Example requirement: When a customer submits an installation request, the system should calculate an estimated service charge based on installation type and priority, reject incomplete requests, and return a clear result.

Before coding, clarify which installation types exist, how priority changes the charge, whether currency rounding applies, and what should happen for an unsupported type. These decisions prevent hidden assumptions from becoming defects.

2. Algorithms and pseudocode

An algorithm is a finite sequence of steps for solving a problem. Pseudocode describes those steps in plain language without committing to a programming language.

For the service-charge example:

INPUT installationType, priority

IF installationType is missing
    RETURN validation error

LOOK UP base charge for installationType

IF installationType is unsupported
    RETURN validation error

IF priority is urgent
    APPLY urgent multiplier

ROUND charge according to currency rules
RETURN final charge

Pseudocode helps developers and business stakeholders agree on behavior before implementation. It also exposes missing rules and edge cases early.

Thinking about complexity

As programs grow, consider how the amount of work changes as the input grows. For example, checking each item in a list once is generally linear, often described as O(n). Comparing every item with every other item can become quadratic, O(n²). These are simplified measures of algorithmic time complexity; actual Salesforce performance also depends on database operations, selectivity, sharing, CPU use and platform limits.

3. Variables, constants and data types

A variable is a named location used by a program to hold a value. A data type defines what kind of value it can represent and which operations are valid.

String customerName = 'Northwind Manufacturing';
Integer installationCount = 4;
Decimal estimatedCharge = 12500.50;
Boolean isApproved = false;
Date requestedDate = Date.today();

These examples use Apex syntax. Similar concepts exist in JavaScript and most programming languages, although syntax and type systems differ.

Apex is strongly typed: variables have declared types and the compiler checks many type errors before execution. Choose types deliberately. For example, use Decimal for currency calculations rather than relying on floating-point arithmetic where exact decimal precision matters.

Constants

A constant represents a value that should not be reassigned after initialization. In Apex, use final to express this intent:

public class InstallationPricing {
    private static final Decimal URGENT_MULTIPLIER = 1.25;
}

Named constants make business rules easier to identify and update than unexplained literal values scattered throughout the code.

4. Operators and expressions

Operators combine values to produce a result. Common categories include:

  • Arithmetic: +, -, *, /, mod.
  • Comparison: ==, !=, >, <, >=, <=.
  • Logical: && (AND), || (OR), ! (NOT).
  • Assignment: =, +=, -=.
  • Conditional: ternary expressions such as condition ? valueA : valueB.
Decimal baseCharge = 10000;
Boolean isUrgent = true;

Decimal finalCharge =
    isUrgent ? baseCharge * 1.25 : baseCharge;

Use parentheses to make complex expressions clear. Avoid compressing several business conditions into one difficult-to-read line.

5. Control flow: decisions and repetition

Control flow determines which statements execute and how often.

Conditional statements

if (installationType == 'Standard') {
    estimatedDays = 5;
} else if (installationType == 'Priority') {
    estimatedDays = 2;
} else {
    throw new IllegalArgumentException(
        'Unsupported installation type'
    );
}

Use if/else for branching logic. A switch statement can be clearer when one expression is compared against several known values.

Loops

List<String> regions = new List<String>{
    'East', 'West', 'North'
};

for (String region : regions) {
    System.debug('Processing region: ' + region);
}

Common loop forms include for, while and enhanced for loops. Choose the form that makes the stopping condition and iteration intent obvious.

Salesforce-specific reminder: Do not perform SOQL queries or DML statements inside loops when processing records. Collect IDs and records, query once where possible, process collections in memory, and perform DML on collections. This is essential for bulk-safe Apex.

6. Methods: give one responsibility a name

A method is a named block of code that performs a task. It can accept parameters and return a value. Methods help divide a large problem into smaller, reusable units.

public class InstallationPricing {
    public static Decimal calculateCharge(
        Decimal baseCharge,
        Boolean isUrgent
    ) {
        if (baseCharge == null || baseCharge < 0) {
            throw new IllegalArgumentException(
                'Base charge must be zero or greater'
            );
        }

        Decimal multiplier = isUrgent ? 1.25 : 1;
        return baseCharge * multiplier;
    }
}

Call the method with explicit inputs:

Decimal charge =
    InstallationPricing.calculateCharge(10000, true);

System.debug(charge); // 12500

A good method name describes the action or result. A method should have a focused responsibility, a clear input contract and a predictable output.

Parameters, return values and side effects

  • Parameters are inputs supplied by the caller.
  • Return values communicate the result back to the caller.
  • Side effects change something outside the method's local calculation, such as updating an sObject or performing DML.

Pure calculation methods are often easier to test because the same inputs produce the same outputs without depending on database state. Keep data access and business calculations separate when that makes the design clearer.

7. Object-Oriented Programming (OOP)

Apex is an object-oriented language. OOP organizes software around classes and objects, combining state (data) and behavior (methods) into understandable units.

Classes and objects

A class is a blueprint; an object is an instance created from that blueprint. A class can define fields, properties, constructors and methods.

public class InstallationRequest {
    public String requestNumber;
    public String installationType;
    public Boolean isUrgent;

    public InstallationRequest(
        String requestNumber,
        String installationType,
        Boolean isUrgent
    ) {
        this.requestNumber = requestNumber;
        this.installationType = installationType;
        this.isUrgent = isUrgent;
    }

    public String getSummary() {
        return requestNumber + ' - ' + installationType;
    }
}

Create an object using new:

InstallationRequest request =
    new InstallationRequest('IR-1001', 'Standard', false);

System.debug(request.getSummary());

The four commonly taught OOP principles

1. Encapsulation

Encapsulation keeps an object's internal state and implementation details behind a controlled interface. In Apex, access modifiers such as private, protected and public help define what other code can access.

public class BankAccount {
    private Decimal balance = 0;

    public Decimal getBalance() {
        return balance;
    }

    public void deposit(Decimal amount) {
        if (amount == null || amount <= 0) {
            throw new IllegalArgumentException(
                'Deposit must be greater than zero'
            );
        }
        balance += amount;
    }
}

Callers cannot directly change the private balance field. They use the public method, where validation can be enforced.

2. Abstraction

Abstraction exposes what a component does while hiding unnecessary implementation detail. An interface is a common way to define a contract without prescribing how every implementation performs the work.

public interface NotificationService {
    void sendNotification(String recipient, String message);
}

A concrete class can implement the contract:

public class EmailNotificationService
    implements NotificationService {

    public void sendNotification(
        String recipient,
        String message
    ) {
        // Email delivery implementation goes here.
    }
}

Another class could implement the same interface using a different delivery channel. The calling code can depend on the contract rather than the specific implementation.

3. Inheritance

Inheritance allows a class to extend another class and reuse or specialize its behavior. Apex supports single class inheritance: a class can extend one class. The parent class must be virtual or abstract to allow extension.

public virtual class PaymentProcessor {
    public virtual String processPayment() {
        return 'Generic payment processing';
    }
}

public class CardPaymentProcessor
    extends PaymentProcessor {

    public override String processPayment() {
        return 'Processing card payment';
    }
}

Use inheritance when there is a genuine “is-a” relationship and a stable shared contract. Do not create deep inheritance trees merely to avoid repeating a few lines of code.

4. Polymorphism

Polymorphism allows different implementations to be used through a common parent type or interface. The same method call can result in different behavior depending on the actual object.

PaymentProcessor processor =
    new CardPaymentProcessor();

System.debug(processor.processPayment());

The variable is typed as the parent class, but the overridden implementation on the concrete object runs. This helps callers work with abstractions instead of hard-coding every implementation type.

8. Composition: build behavior from collaborating components

Composition means a class uses other objects to perform parts of its work. It is often a flexible alternative to inheritance.

For example, an Installation Service may use a Pricing Service, a Notification Service and a Repository. Each component owns a focused responsibility, and the service coordinates them.

public class InstallationService {
    private InstallationPricing pricing;

    public InstallationService(InstallationPricing pricing) {
        this.pricing = pricing;
    }

    public Decimal estimate(
        Decimal baseCharge,
        Boolean urgent
    ) {
        return pricing.calculateCharge(baseCharge, urgent);
    }
}

This example illustrates dependency injection through a constructor. In a larger system, interfaces can make dependencies replaceable and easier to test.

9. Clean code: make intent obvious

Code is read and changed more often than it is first written. Clean code reduces the effort needed to understand behavior and safely make changes.

  • Use meaningful names: calculateDiscount() communicates more than doWork().
  • Keep methods focused: avoid mixing validation, querying, calculations, notifications and DML in one large method.
  • Avoid unexplained literals: use named constants for business thresholds and fixed values.
  • Reduce duplication: extract genuinely reusable logic, but do not create abstractions for every two-line operation.
  • Prefer clear conditions: break complex Boolean expressions into named variables or focused methods.
  • Document why, not the obvious what: comments should explain business context, constraints or non-obvious decisions.
  • Keep responsibilities separate: data access, business rules and presentation concerns should not become unnecessarily entangled.
  • Handle errors deliberately: validate inputs and provide useful, actionable error behavior.

A practical naming example

// Hard to understand
Decimal x = a * 0.15;

// Easier to understand
Decimal partnerDiscountRate = 0.15;
Decimal partnerDiscount = orderAmount * partnerDiscountRate;

Prefer clarity over cleverness. A few extra lines are worthwhile when they make business behavior easier to review.

10. Exceptions and defensive programming

Programs must handle invalid input and unexpected conditions. An exception represents an error or exceptional condition that interrupts normal execution.

public static Decimal calculateTax(Decimal amount) {
    if (amount == null) {
        throw new IllegalArgumentException(
            'Amount is required'
        );
    }

    if (amount < 0) {
        throw new IllegalArgumentException(
            'Amount cannot be negative'
        );
    }

    return amount * 0.18;
}

Use try/catch when you can meaningfully handle or translate an exception. Do not catch every exception just to suppress it. Preserve useful context and choose whether the caller should receive a clear error or whether the operation should fail.

11. Testing: prove behavior, not just execution

Testing checks whether code behaves as expected for normal, boundary and invalid inputs. A good test should make the expected behavior explicit through assertions.

@IsTest
private class InstallationPricingTest {
    @IsTest
    static void calculatesUrgentCharge() {
        Decimal actual =
            InstallationPricing.calculateCharge(10000, true);

        System.assertEquals(
            12500,
            actual,
            'Urgent charge should include the 25% multiplier'
        );
    }

    @IsTest
    static void rejectsNegativeCharge() {
        try {
            InstallationPricing.calculateCharge(-100, false);
            System.assert(false, 'Expected validation exception');
        } catch (IllegalArgumentException ex) {
            System.assert(
                ex.getMessage().contains('zero or greater')
            );
        }
    }
}

These tests illustrate a successful calculation and a validation failure. Real projects should also test boundary values, nulls, rounding rules and relevant integration or database behavior. Keep business logic testable without requiring unnecessary org data.

13. Hands-on exercises

Exercise 1 — Pricing calculator: Create an Apex class that accepts a base amount and installation priority. Calculate a surcharge, validate invalid inputs and return a Decimal result. Add tests for normal, urgent, zero and negative amounts.
Exercise 2 — Request model: Create an InstallationRequest class with request number, type and priority. Add a constructor and a method that returns a readable summary. Make internal fields private and expose controlled access.
Exercise 3 — Notification abstraction: Define a NotificationService interface. Implement two concrete classes—Email and In-App. Write a service that accepts the interface rather than depending on one concrete implementation.
Exercise 4 — Refactor: Take a single long method that validates input, calculates a charge and builds a message. Split it into focused methods with meaningful names. Compare readability and testability before and after.
Exercise 5 — Edge cases: For the pricing calculator, list at least eight edge cases before coding. Include nulls, zero, negative values, unusually large amounts, unsupported priorities and rounding behavior.

Key takeaway

Programming fundamentals are the foundation beneath every Salesforce implementation. Learn to break down problems, choose appropriate data types, control execution, create focused methods, model behavior with objects and use OOP principles deliberately. Combine those skills with clean code, defensive programming and meaningful tests—and your Apex solutions will be easier to extend, debug and maintain.

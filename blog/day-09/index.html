SOQL Deep Dive: Query Design, Relationships, Aggregates and Selectivity

A practical guide to designing efficient SOQL queries, navigating parent-child relationships, using aggregate functions and improving query selectivity in Salesforce.

Intermediate20–25 min readUpdated: November 2026

SOQL (Salesforce Object Query Language) is the primary way to retrieve records from Salesforce objects. Writing a query that returns the right rows is only the beginning: production-quality query design also considers relationships, aggregation, security, selectivity, row volume and how the result will be consumed.

Core idea: Start from the business question, identify the smallest useful dataset, select only the fields and related records you need, and validate the query plan when data volume matters.

1. SOQL query anatomy

SELECT Id, Name, Industry
FROM Account
WHERE Industry = 'Manufacturing'
ORDER BY Name
LIMIT 100

SELECT defines fields, FROM identifies the object, WHERE filters rows, ORDER BY sorts the result, and LIMIT caps returned records. SOQL is not SQL: it queries Salesforce object data and relationship structures, and it does not support arbitrary joins.

Design queries from requirements

  • Write down the required output before choosing fields.
  • Filter as close to the data source as possible instead of querying broadly and filtering in Apex.
  • Use deterministic ordering when the caller depends on sequence; add a tie-breaker such as Id if needed.
  • Use LIMIT for bounded screens or previews, not as a substitute for a complete large-data processing strategy.
  • Bind Apex variables rather than concatenating user input into query strings.

2. Filtering, operators and bind variables

String targetIndustry = 'Manufacturing';
Set<Id> accountIds = new Set<Id>();

// Populate accountIds from validated application context.
List<Contact> contacts = [
    SELECT Id, Name, Email, AccountId
    FROM Contact
    WHERE AccountId IN :accountIds
      AND Email != null
      AND Name LIKE :('%' + 'son' + '%')
    ORDER BY Name
];

Common operators include =, !=, comparison operators, IN, NOT IN, LIKE, INCLUDES and EXCLUDES for multi-select picklists. Use parentheses to make mixed AND/OR logic explicit.

In static SOQL, bind variables use a colon (for example, :accountIds). For dynamic SOQL, use Database.queryWithBinds with an explicit bind map where supported, and allowlist dynamic object names, field names and sort directions. Bind variables protect values; they do not make arbitrary query structure safe.

3. Relationship queries

Salesforce relationships let a query retrieve related records without writing separate queries for every row. There are two common directions.

Child-to-parent: dot notation

List<Contact> contacts = [
    SELECT Id, Name, AccountId,
           Account.Name, Account.Industry,
           Account.Owner.Name
    FROM Contact
    WHERE Account.Industry = 'Manufacturing'
];

Use relationship field names to traverse from a child to its parent. Custom relationship fields typically use the relationship name ending in __r, rather than the field API name ending in __c.

Parent-to-child: subquery

List<Account> accounts = [
    SELECT Id, Name,
           (SELECT Id, FirstName, LastName, Email
            FROM Contacts
            WHERE Email != null
            ORDER BY LastName
            LIMIT 10)
    FROM Account
    WHERE Industry = 'Manufacturing'
];

The child relationship name (here, Contacts) is used in the subquery. For custom relationships, confirm the exact child relationship name in Object Manager or schema metadata. Parent-to-child subqueries return a child relationship collection; account for its size and avoid selecting excessive child rows.

Relationship query vs separate queries

Use relationship queries when the related data naturally belongs in one response and the row volume is bounded. Use separate queries and Maps when you need independent filtering, reuse related data across multiple processing steps, or must control query shape and volume more precisely.

4. Semi-joins and anti-joins

A semi-join filters one object based on the existence of related records. An anti-join filters for the absence of related records.

// Accounts that have at least one open Case
List<Account> accountsWithOpenCases = [
    SELECT Id, Name
    FROM Account
    WHERE Id IN (
        SELECT AccountId
        FROM Case
        WHERE IsClosed = false
          AND AccountId != null
    )
];

// Accounts that have no Contacts
List<Account> accountsWithoutContacts = [
    SELECT Id, Name
    FROM Account
    WHERE Id NOT IN (
        SELECT AccountId
        FROM Contact
        WHERE AccountId != null
    )
];

These patterns can express existence logic in one query rather than retrieving broad datasets and comparing them in Apex. Semi-join restrictions apply: not every object/field combination or nested form is supported, so verify the query against the current SOQL reference.

5. Aggregate queries and GROUP BY

Aggregate functions calculate summaries in the database. Common functions include COUNT(), COUNT(field), SUM(), AVG(), MIN() and MAX().

List<AggregateResult> summaries = [
    SELECT AccountId accountKey,
           COUNT(Id) caseCount,
           MIN(CreatedDate) firstCase,
           MAX(CreatedDate) latestCase
    FROM Case
    WHERE AccountId != null
    GROUP BY AccountId
    HAVING COUNT(Id) > 3
];

for (AggregateResult row : summaries) {
    Id accountId = (Id) row.get('accountKey');
    Integer totalCases = (Integer) row.get('caseCount');
    System.debug(accountId + ': ' + totalCases);
}

Grouped queries return AggregateResult, not ordinary sObjects. Give grouped expressions aliases to make retrieval clear. WHERE filters source rows before grouping; HAVING filters groups after aggregation.

COUNT() vs COUNT(field)

COUNT() counts matching rows. COUNT(SomeField) counts rows where that field is non-null. Be deliberate about null behavior when validating totals.

Aggregate by multiple dimensions

List<AggregateResult> pipeline = [
    SELECT StageName stage, Type dealType,
           SUM(Amount) totalAmount,
           COUNT(Id) opportunityCount
    FROM Opportunity
    WHERE IsClosed = false
    GROUP BY StageName, Type
    ORDER BY StageName
];

Use aggregates when the application needs summaries rather than every underlying record. This reduces data transferred to Apex, but grouped result limits and aggregate-query constraints still apply.

6. Query selectivity and performance

A selective query narrows the candidate records efficiently. On large objects, a broad filter can cause a table scan or exceed platform query constraints even if the final result appears modest.

  • Filter on indexed fields where appropriate, such as record IDs, foreign keys, audit fields or configured custom indexes.
  • Prefer equality or bounded range filters when they match the business requirement; a filter's presence alone does not guarantee selectivity.
  • Be careful with leading-wildcard patterns such as LIKE '%term', negative filters such as !=/NOT, and complex OR conditions. They may prevent efficient index use.
  • Avoid unnecessary fields, relationship traversals and unbounded child subqueries.
  • Use Query Plan in Developer Console or supported tooling to inspect candidate plans, leading operations and relative cost.
  • Test with production-like data distribution. A query that performs well in a small sandbox may behave differently in a large org.
Important: An indexed field does not automatically make a query selective. The optimizer evaluates filter shape, data distribution, statistics and platform rules. Use Query Plan rather than relying on assumptions or memorized threshold numbers.

7. SOQL in Apex: bulk and security considerations

public with sharing class AccountContactService {
    public static List<Contact> getContacts(Set<Id> accountIds) {
        if (accountIds == null || accountIds.isEmpty()) {
            return new List<Contact>();
        }

        return [
            SELECT Id, Name, Email, AccountId
            FROM Contact
            WHERE AccountId IN :accountIds
            WITH USER_MODE
            ORDER BY Name
        ];
    }
}

Keep SOQL outside loops and query once for the collection of IDs. In modern Apex, WITH USER_MODE can enforce object- and field-level access for the query; choose the security approach deliberately for the use case. with sharing addresses record-level sharing, not CRUD/FLS by itself. For graceful field stripping or legacy patterns, evaluate Security.stripInaccessible and the relevant user/system mode behavior.

For large data volumes, use Batch Apex, QueryLocator-based processing or other appropriate asynchronous patterns instead of trying to load every matching row into one in-memory List. Remember that SOQL row limits, heap, CPU and transaction boundaries still apply.

8. Common mistakes to avoid

  • Using SELECT *—SOQL requires explicit fields.
  • Querying inside loops and causing avoidable query-limit failures.
  • Retrieving every field or every child record when only a small subset is needed.
  • Building dynamic SOQL by concatenating untrusted values.
  • Assuming with sharing enforces object and field permissions.
  • Using WHERE and HAVING interchangeably.
  • Ignoring null values in aggregate calculations and relationship filters.
  • Assuming a query is selective because it uses an indexed field without checking the actual query plan.

9. Hands-on exercises

  7. Compare two query plans with different filters in a data-rich org.

Key takeaway

Strong SOQL is not about writing the longest query. It is about expressing the data requirement precisely, navigating relationships correctly, aggregating at the database layer when useful, and validating selectivity and security. Query only what the application needs—and design for the data volume the org will actually contain.
